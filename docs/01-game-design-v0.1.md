# 《电梯求生》游戏设计共识 v0.1

**文档状态：** 前期设计基线

**用途：** 产品设计、技术架构和 Codex 开发交接

**原则：** 本文记录已确认的总体方向，以及明确标注为候选、倾向或待设计的未决事项。已确认决策以 `docs/05-design-decisions.md` 为最终依据。

---

## 1. 产品定位

《电梯求生》是一款以网页为首发平台的单人策略生存 Roguelite 游戏。

玩家从异常电梯中枢进入不同的灾难或异常世界，在有限天数内探索场景、收集资源、处理事件、与敌人战斗，并完成世界主线任务后返回中枢。

核心体验不是纯战斗，也不是单纯搜集，而是：

- 在不完全信息下做判断；
- 管理时间、背包、负重、状态和消耗品；
- 在普通发育与主线推进之间取舍；
- 判断是否继续深入或及时撤离；
- 为前期决策承担后期结果；
- 完成一局后获得长期成长和世界收藏。

游戏参考“无限流”的任务世界结构，但使用原创世界、原创角色和原创设定，不直接套用现有影视、小说或游戏IP。

---

## 2. 长期游戏结构

长期循环为：

```text
异常电梯中枢
→ 选择任务世界
→ 进入一个有明确规则和期限的世界
→ 探索、发育并完成主线
→ 返回中枢
→ 获得结算评级和永久奖励
→ 解锁新的能力、遗物、情报或世界
→ 进入更高难度任务
```

一个完整“单局”指一次完整的任务世界，而不是单独进入一个房间或楼层。

未来世界可以包括：

- 感染隔离区；
- 极寒世界；
- 洪水世界；
- 异常酒店；
- 地下实验设施；
- 太空站或其他规则型世界。

不同世界更换资源和特殊状态，但尽量复用底层的时间、背包、装备、状态、事件和战斗系统。

---

## 3. 首版总体范围

首版只做一个完整任务世界，用于验证核心闭环。

当前首个世界方向为：

> 感染灾变或感染隔离区。

首版采用：

- 单人角色；
- 无幸存者队伍；
- 无多人合作；
- 无玩家交易；
- 无复杂家园建设；
- 无实时开放世界；
- 无战术格子地图；
- 以文字、UI、场景插画和节点网络呈现探索。

未来可以考虑加入2D战术格子场景，但不属于首版范围。

---

## 4. 单局目标与期限

单局以期限驱动。

当前任务结构为：

> 玩家需要在有限天数内收集若干关键部件、材料或信息，修复或启动电梯，并在最终危机前逃离当前世界。

主线目标是完成逃生；时间期限与最终危机负责施加压力。

当前首版采用七个游戏日的结构。

玩家不能无限留在世界中发育。随着日期推进：

- 食物等生存资源持续消耗；
- 世界威胁不可逆地上升；
- 部分地点或机会可能消失；
- 最终危机逐渐接近。

这样避免“先无限刷装备，最后再做主线”成为固定最优策略。

---

## 5. 单局时长

目标时长：

```text
熟练玩家：30～40分钟
普通玩家：40～50分钟
首次游玩：50～60分钟
合理总体范围：30～60分钟
```

完整体验的设计中位数约为40～50分钟。

由于是单人游戏，玩家不需要连续完成整局。

游戏支持：

- 回合制或选择制的天然暂停；
- 自动保存；
- 中断本局；
- 下次继续当前任务。

不使用现实时间倒计时作为主要压力。

评分依据游戏内日期、游戏内时间和资源使用情况，而不是玩家现实中花费了多少分钟。

---

## 6. 每日循环

每天只能选择一个主要场景。

单日流程为：

```text
开始一天
→ 查看世界变化、任务进度和角色状态
→ 查看当天候选场景
→ 选择当天唯一的主要场景
→ 配置装备和背包
→ 进入场景
→ 探索多个节点
→ 主动撤退或被迫撤退
→ 返回异常电梯
→ 治疗、制作、维修和整理
→ 结束当天
```

选择场景后，当天不能撤回电梯再改选另一个场景。

撤离当前场景不会自动恢复当天的场景选择次数。

这使场景选择具有承诺成本，也让出发前整备成为核心策略。

---

## 7. 场景与节点

每个主要场景由一个节点网络构成，而不是简单的一次随机事件。

首版每个场景预计包含约4～6个节点，玩家通常只能在一天内处理其中一部分。

节点可能承担：

- 资源搜索；
- 路线连接；
- 障碍或门槛；
- 信息获取；
- 战斗遭遇；
- 特殊事件；
- 剧情内容；
- 主线或可选目标。

玩家能够在场景内部移动、探索多个节点并选择撤退。

移动、搜索、破解、治疗和其他行为消耗游戏内时间。

返程同样需要时间。玩家不能在最深节点中瞬间返回电梯，因此必须预留撤离时间。

节点网络是首版核心玩法，但以下细节尚未最终确定：

- 场景结构展示到什么程度；
- 未探索节点如何揭示；
- 重复经过节点是否再次消耗完整时间；
- 节点危险如何动态变化；
- 场景内威胁值和噪声的具体算法。

---

## 8. 场景情报

每天选择场景时，基础信息必须足够玩家进行合理判断。

必定公开：

- 场景名称；
- 主要资源倾向；
- 模糊危险范围。

例如：

```text
隔离医院
主要资源：药品、医疗材料
危险评估：中等～较高
```

主要资源表示可靠的资源倾向，而不是保证具体数量。

危险评估保留一定波动，不显示精确答案。

额外信息可以来自：

- 玩家专长；
- 扫描或侦察工具；
- 特殊事件；
- 档案；
- 先前场景获得的线索；
- 跨场景状态变化。

场景真实状态与玩家已掌握的情报必须分开保存。

情报可以存在偏差，但偏差应当有可理解的来源，例如：

- 情报过期；
- 信号干扰；
- 敌人迁徙；
- 世界事件；
- 特殊敌人能力。

基础系统不应无提示地欺骗玩家。

---

## 9. 跨场景联动

不同场景属于同一个任务世界，不应完全彼此独立。

玩家可以在一个场景中获得影响另一个场景的信息，例如：

- 资源位置；
- 钥匙或密码线索；
- 隐藏入口；
- 路线信息；
- 场景特殊规则；
- 敌人行为规律。

某个场景中的行动也可以改变另一个场景，例如：

```text
恢复变电站供电
→ 医院照明恢复
→ 搜索耗时降低
→ 某些电子门开启
→ 同时唤醒部分感染者
```

首版控制联动规模，避免制作复杂的全世界模拟。

---

## 10. 玩家角色与专长

首版角色拥有固定的基础属性，不做角色创建、自由属性加点和复杂职业系统。

每局开始前，从三个专长中选择一个：

### 侦察专长

定位：

- 提高情报质量；
- 缩小危险评估范围；
- 揭示额外场景信息；
- 提供侦察相关事件选项。

### 工程专长

定位：

- 维修、拆解和破解；
- 降低工具使用成本；
- 提供工程类障碍解决方案；
- 提升部分材料利用率。

### 生存专长

定位：

- 提高治疗、补给或伤势处理效率；
- 增加环境适应能力；
- 提供撤退和求生类事件选项。

专长在本局内不能更换。

所有专长必须能够完成主线；专长只改变解决问题的方法、风险和资源成本，不能成为通关资格锁。

首版以被动效果和特殊选项为主，不急于加入复杂主动技能。

未来再加入：

- 永久成长；
- 专长分支；
- 可装配能力；
- 横向构筑选择。

---

## 11. 玩家状态系统

首版状态不做过度模拟，以少量具有清晰影响的状态为主。

根据 DEC-026，首版核心生存状态包括：

- 生命；
- 流血；
- 伤势；
- 感染暴露；
- 感染进展；
- 饱食。

生命、伤势和感染是独立问题，感染暴露与已经形成的感染进展也分开处理。饱食是主要在每日结算中消耗的日级资源。

首版不实现口渴、体温、士气、精神、睡眠和身体部位系统。具体状态数值等待后续平衡。

感染相关状态是感染世界的特殊状态，而不是所有世界永久存在的固定属性。

未来不同世界可以用同一机制加载不同状态，例如：

- 感染；
- 低温暴露；
- 污染；
- 缺氧；
- 辐射；
- 精神异常。

首版每项状态只关联一到两个明确机制，避免形成难以解释的复杂连锁反应。

---

## 12. 状态与效果架构

状态系统采用：

```text
基础状态
→ 阈值或条件规则
→ 标准化效果
→ 行为结算
```

基础状态只保存事实，例如：

```text
生命为38
饱食为17
感染为42
当前存在流血
```

状态本身不直接修改其他系统。

规则层根据状态范围产生效果，例如：

```text
严重饥饿
→ 当日自然恢复失效

感染发作
→ 治疗效率降低

骨折
→ 移动与撤离耗时增加
```

行为发生时，结算系统统一收集：

- 专长效果；
- 装备效果；
- 状态效果；
- 世界规则；
- 临时效果。

然后计算最终结果。

不采用各项指标任意互相监听、互相修改的架构，以避免循环依赖和难以追踪的结果。

---

## 13. 背包与物品容器

物品分布在三个容器中：

### 电梯仓库

保存当前单局已经带回的资源，用于：

- 每日整备；
- 制作；
- 维修；
- 治疗；
- 主线任务。

### 随身背包

进入场景时携带。

背包采用有限网格：

- 不同物品占据不同数量和形状的格子；
- 小型同类资源可以有限堆叠；
- 武器、防具、工具和关键物品通常不可堆叠；
- 任务物品也占空间。

### 装备栏

当前穿戴或手持的物品不占背包格子。

备用装备仍需放入背包。

首版装备栏方向为：

- 武器位；
- 防具位；
- 实用装备位；
- 两个快捷物品位。

快捷位提供更低的紧急使用成本，但不会凭空增加背包容量。

---

## 14. 物品重量

已确认需要认真考虑物品重量，但具体方案尚未最终锁定。

当前倾向方案为：

> 格子表达体积，重量表达行动负担。

当前装备栏中的武器、防具和实用装备不占背包格子，也不计入背包负重；备用装备放入背包后，按照物品尺寸和重量正常计算。

首版建议使用简单负重分档，而不是精确到每一点重量都改变大量公式。

可能的首版影响范围：

- 节点移动时间；
- 撤离时间；
- 严重超载时的逃跑效率。

以下具体内容仍需确认：

- 基础承重数值；
- 各负重区间；
- 是否允许短暂超载；
- 超载倍率；
- 专长和伤势如何影响承重。

---

## 15. 装备设计原则

首版装备不做：

- 白、绿、蓝、紫等品质等级；
- 随机词条；
- 随机属性浮动；
- 套装系统；
- 大量百分比属性；
- 同一装备的纯数值升级版本。

每件装备具有固定、清晰和可预期的战术定位。

装备的价值主要来自：

- 提供新的行动；
- 解锁新的节点解决方案；
- 改变风险和资源成本；
- 改变战斗节奏；
- 对特定环境提供防护。

装备不只是“增加攻击力”。

每件装备需要明确：

- 主要用途；
- 最适合的场景；
- 主要代价；
- 可解决的节点类型；
- 额外用途；
- 明确弱点。

未来可以出现特殊装备或遗物，但它们应当是具有独特规则的独立物品，而不是普通装备增加随机数值后的高品质版本。

---

## 16. 武器、防具与工具定位

### 武器

主要解决战斗问题。

核心维度预计包括：

- 伤害；
- 行动时间；
- 噪声；
- 耐久；
- 特殊行动或标签。

不同武器应提供不同战斗行动，而不是只修改攻击力。

首版暂不优先实现枪械，以避免过早引入弹药、换弹、命中、射程和枪械管理系统。

### 防具

主要在以下方向间取舍：

- 直接伤害防护；
- 感染或污染防护；
- 行动效率；
- 耐久。

首版采用单一主要防具位，不拆分头盔、手套、鞋子等大量槽位。

### 工具

工具是探索系统的重要组成部分，用于：

- 破解；
- 撬门；
- 维修；
- 扫描；
- 照明；
- 环境防护；
- 获取额外情报。

工具应当解锁解决方案，同时带来重量、格子、耐久、时间、噪声或能源成本。

首版只有一个实用装备位，可以装备手持工具、探测设备、照明设备或穿戴式功能设备，以保证出发前存在真实取舍。

---

## 17. 装备耐久

耐久可以存在，但必须服务策略，而不是成为频繁维修的机械负担。

耐久应当在关键使用中产生有感知的消耗，例如：

- 普通攻击；
- 重击；
- 破坏障碍；
- 强行撬锁；
- 防具成功抵挡伤害。

装备损坏后不必立即消失，可以进入失效或严重损坏状态，并允许：

- 带回维修；
- 拆解；
- 放弃。

具体耐久数值和维修经济尚未确定。

---

## 18. 资源经济原则

首版资源压力主要来自：

```text
游戏内时间
+ 背包空间
+ 负重
+ 持续消耗
+ 场景风险
```

玩家不需要搜空每个场景。

核心决策应当是：

> 哪些资源值得花时间获取，哪些值得占用空间，哪些必须带走，什么时候应该停止搜索并撤离。

当前资源类别方向包括：

- 生存资源；
- 制作材料；
- 装备；
- 主线任务物品；
- 情报；
- 可跨局保存的永久奖励或收藏品。

首版不需要复杂货币和交易经济。

资源生成应当符合场景逻辑，通过：

```text
场景模板
+ 内容标签
+ 资源预算
+ 权重
+ 保底规则
```

生成，而不是完全无约束随机。

制作系统首版只保留少量高价值、用途明确的配方。

评分奖励任务效率和合理决策，不奖励机械地搜空所有节点。

---

## 19. 探索与战斗关系

探索是游戏主体。

战斗是风险处理方式之一，而不是全部内容。

玩家可以通过：

- 情报；
- 工具；
- 路线；
- 资源交换；
- 特殊事件选项；
- 撤退；

避免或降低部分战斗风险。

根据 DEC-025，首版最小战斗模型已确认为：

- 一名玩家；
- 一个敌人实体；
- 少量明确行动；
- 可以尝试逃跑。

首版采用无站位的CTB行动时间轴：

- 每个角色拥有下一次行动时间；
- 不同行动拥有不同时间成本；
- 快速角色可能更频繁行动；
- 重型行动威力高但耗时更长。

这一战斗方向尚未最终锁定，仍需完成最小战斗规则设计。

未来战术地图中的移动能力与战斗行动频率应当分离，避免一个“速度”属性同时控制所有优势。

---

## 20. 撤退原则

撤退是合法且重要的策略。

玩家能够：

- 在场景探索中主动返程；
- 在风险过高时放弃剩余节点；
- 在战斗中尝试逃跑；
- 带着有限收益结束当天。

战略撤退不应天然降低评级。

评级可以惩罚：

- 无意义地浪费资源；
- 不必要地承受伤势；
- 未完成主线；
- 极低效率。

但不应惩罚合理止损。

---

## 21. 结算与评级

单局结束采用：

```text
S / A / B / C / D / E / F
```

评级综合考虑：

- 主线完成度；
- 是否存活；
- 游戏内完成时间；
- 资源效率；
- 伤势与状态；
- 可选任务；
- 特殊发现；
- 隐藏结局。

除字母评级外，未来可以增加风格标签，例如：

- 谨慎求生者；
- 高风险探索者；
- 情报专家；
- 极限撤离者；
- 资源管理者。

死亡不一定机械地全部判定为F。最终阶段的特殊牺牲或剧情结局，可以获得特殊结算。

永久奖励不应让高评级玩家形成不可逆的强者滚雪球。

---

## 22. 自动保存与运行存档

首版采用：

```text
永久档案
+ 当前唯一单局存档
```

游戏在重要不可逆操作后自动保存，例如：

- 选择场景；
- 移动节点；
- 完成搜索；
- 战斗行动结算；
- 获得或消耗物品；
- 返回电梯；
- 结束一天；
- 完成结算。

玩家可以退出并继续当前任务，但不能自由创建多个局内存档点，也不能随意回滚到之前的选择。

首版本地Web游戏不投入复杂反作弊。

## 23. 异常电梯中枢

异常电梯是：

- 不同任务世界的连接点；
- 永久成长的承载空间；
- 遗物和档案的保存地点；
- 长期收藏与归属感的核心；
- 未来玩家互动的入口。

### 首版功能

只实现功能化中枢：

- 任务终端；
- 强化终端；
- 遗物柜；
- 档案或历史记录；
- 单局仓库与整备入口。

表现形式可以是固定背景插画加功能区域，不做角色自由行走。

### 长期扩展

未来可以增加：

- 空间主题；
- 家具和装饰；
- 不同世界带回的材料；
- 纪念品和奖杯；
- 遗物展示；
- 中枢扩建；
- 玩家拜访；
- 点赞或预设留言；
- 异步展示互动。

长期优先考虑轻量、异步社交。

暂不考虑：

- 实时多人房间；
- 自由交易；
- 强力资源赠送；
- 中枢掠夺；
- 复杂实时聊天。

装扮与永久战斗强度原则上分离，避免家园装饰成为强制数值系统。

## 24. 永久成长

长期成长以 Roguelite 为方向。

永久成长优先采用横向解锁，而不是不断叠加基础数值。

可能包括：

- 装备蓝图；
- 新的专长能力；
- 世界档案和永久情报；
- 新任务世界；
- 新的解决方案；
- 遗物槽；
- 少量跨局携带的特殊物品。

首版只需非常克制地实现一种永久资源和少量解锁。

当前中枢能源是首版永久资源的候选名称。

失败后仍应保留少量永久进度或知识，避免新玩家连续失败后完全停滞。

## 25. 程序生成与AI生成

核心世界生成必须由可验证的规则引擎完成。

程序生成使用：

- 确定性随机种子；
- 场景模板；
- 内容池；
- 标签；
- 资源和危险预算；
- 依赖关系；
- 保底规则；
- 生成后验证。

必须保证：

- 关键物品可获得；
- 主线不存在死锁；
- 至少存在一条合理通关路线；
- 早期难度可承受；
- 关键内容不会因随机而永久缺失；
- 同一种子能够重现。

AI不直接决定基本平衡、胜利条件和关键数值。

长期AI更适合：

- 生成事件文案；
- 生成任务包装；
- 生成世界背景；
- 生成符合结构约束的候选内容；
- 在既有规则骨架上提供叙事变化。

AI生成内容必须经过结构校验和规则验证。

建议发展顺序：

```text
人工配置内容
→ AI辅助离线撰写
→ Schema校验后的候选内容
→ 人工审核的周期任务
→ 更远期的运行时个性化叙事
```

## 26. 技术架构

首版技术方向：

- React；
- TypeScript；
- Vite；
- Zustand作为UI状态适配层或轻量状态管理；
- Zod验证数据配置；
- Vitest测试核心规则。

暂不引入 Phaser。

如果未来验证战术地图，可以先使用：

- React CSS Grid；
- SVG；
- 其他轻量二维呈现。

是否引入专用游戏引擎，在确认需求后再决定。

### 核心架构原则

游戏规则必须是纯TypeScript，并与React界面分离。

```text
React UI
→ 发出游戏命令
→ 纯TypeScript规则引擎结算
→ 返回新状态和事件日志
→ React展示结果
```

React组件不能直接编写核心游戏结算规则。

### 随机系统

所有随机行为使用统一的可注入随机数生成器和种子。

禁止在业务代码中零散调用 `Math.random()`。

### 数据驱动

以下内容尽量通过配置定义：

- 物品；
- 武器；
- 防具；
- 工具；
- 状态；
- 效果；
- 敌人；
- 场景；
- 节点；
- 事件；
- 任务目标；
- 永久解锁。

## 31. 首个纵向切片目标

纵向切片不需要直接实现完整七天。

第一段可玩验证可以是：

```text
进入异常电梯
→ 选择一个专长
→ 从三个场景中选择医院
→ 配置固定装备与背包
→ 探索一张4～6节点的医院地图
→ 搜索资源
→ 处理一个障碍事件
→ 完成一次最小战斗
→ 判断继续深入或撤离
→ 带着物资返回电梯
→ 完成一次日结算
→ 自动保存
```

这个切片能够验证：

- 场景选择；
- 情报；
- 整备；
- 背包；
- 重量；
- 节点探索；
- 时间压力；
- 事件；
- 战斗；
- 撤退；
- 日结算；
- 存档。

验证成功后，再扩展到完整七日世界。
