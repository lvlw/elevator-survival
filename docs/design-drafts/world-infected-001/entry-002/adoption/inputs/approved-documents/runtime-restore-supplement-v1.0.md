## 2. 已批准的恢复与事务边界

冷启动没有现存内存历史，不应伪造“独立当前期望”。允许新增受控冷候选解析入口，使用严格根角色、受控内容／规则声明与整档内部一致性检查；返回候选，没有安装权。原 `restoreMissionCandidate(raw, expected, scope)` 及K18/K19同进度恢复要求保留，expected不能改可选，也不从候选复制一份冒充独立证据。

唯一应用状态持有者负责一次bootstrap／完整校验／一次安装；只有真正成功读取null才能进入无档首次创建路径。损坏、不兼容或读取失败不得兜底重建角色。已有当前状态时禁止第二bootstrap、旧快照replace及重建空事实绕过关闭。

规则体系在明确、有序、确定性的编排中提出计划，由唯一入口合成完整身体／物品／周期／任务后态；涉及经济和终局的入口，必须等真实业务全部可完成后再开放。不能先提交closed再依赖监听器补奖罚。一次完整提交、一次保存尝试、一次只读通知；写失败保留已提交内存并单独报错，不重放玩法。

冷候选、单owner或Object.freeze均不是绝对离线防篡改／防回滚。多标签与浏览器IO必须在公开接线前实际验证；首批headless支持矩阵可以显式拒绝未支持阶段，但不能永久删除战斗保存、终局或角色延续责任。

O2批准的是上述规则与合同边界，不是提前创建完整Profile、通用任务SDK、跨世界供给、全量存档架构或新增玩家入口。具体新接口名、版本ID、文件路径以对应工程任务明确为准。

## 3. 落地职责映射，不另造玩法

| 边界 | 后续必须落实的责任 | 本次不授予的能力 |
| --- | --- | --- |
| 窄值／内容绑定 | 受控内容声明核对角色、世界、模板、具体委托、执行及受支持版本；冷候选不假装持有不存在的当前历史 | 候选自证、隐式补未接、关闭后reopen、旧档静默升级 |
| 唯一当前事实 | 同一角色的身体、周期、具体委托事实、位置、实体与持续现场在完整稳定态中由唯一应用持有者提交；派生／引用不是第二可写真相 | 让UI或订阅者分别维护身体、关闭账、物品或来源库存 |
| 首次与冷安装 | 成功读取null才建立首次创建前提；合法全档通过验证后一次安装；已有current禁止第二bootstrap或任意replace | 读取错误兜底new；用一份可解析未接候选覆盖已有关闭事实 |
| ready与时序 | 最新期限关闭／执行／已结周期与当前角色周期联合验证；正常返回待结、首次D1、活动D/T、已消费后续周期分别处理 | 永久免检布尔、第二关闭账、未验证旧ready免除新周期 |
| 完整规则事务 | 受控意图、新鲜度、全部前提→确定性规则计划→完整后态验证→一次提交→一次保存尝试→一次只读通知 | 半笔关闭后靠异步监听补发奖罚，保存失败重跑规则 |
| 未支持阶段 | headless阶段明示支持子集与拒绝，生产入口不接；真实终局、战斗保存与角色延续责任保留 | 无业务却以测试占位结果开放玩家操作，或永久删掉后续能力 |

R1的start_cycle／end_cycle／end_day／bridge用于解释有限模型的联合校验。生产实现应在本期受支持表示上保持这些关系或等价保障；获批的是最小唯一事实与严格绑定，不是要求G1先建立全角色历史、通用任务框架或把有限顺序模型作为未来全部世界的永久约束。

## 4. 与G1及后续工程的分工

[G1](energy-cycle-contract-v1.0.md)只输出单精力与身体周期的纯结果；它不持有全角色数据，不产生实际任务结果，不调用持久化或安装，不以自己的局部校验冒充全聚合验证。

持续现场与冷恢复／安装必须分别在相应工程完成后按准确SHA实审。具体受控冷候选入口只在届时任务明确白名单后新增；原公开restore及旧K测试不得为了方便接线而放宽或删除。完整终局事务依赖真实身体、物品和经济处置，业务未齐备前不得开放对应产品入口。
