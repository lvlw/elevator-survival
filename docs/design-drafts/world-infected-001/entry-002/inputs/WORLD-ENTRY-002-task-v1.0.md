明确受控意图 → 完整前提校验 → 规则体系按确定顺序提出效果／计划 → 组合验证完整后态 → 唯一提交 → 一次保存尝试与一次只读状态通知的关系。沿用已有保存失败不重跑玩法的原则；通知不补发奖罚、不推进周期、不追加写值。

不能先单独把委托closed提交，再寄望之后补身体、物品或收支。正常返回、Day7截止、死亡、新任务出发衔接各自提供完整事务的接口图；如果对应业务尚未批准或未实现，实际产品入口保持未接线，不让“不属于这次实现”变成可以提交半套结算。

战斗中的稳定可保存点、动作后的立即结果、未结算终局不得含糊。不能为保存方便规定“只能出战斗才保存”，也不能把正在结算的半成品暴露成可加载状态。现阶段究竟支持哪些完整输入与状态，由近期工程契约明确；未支持状态要诚实拒绝，不静默改义。

### 4.4 新旧版本与发布安排

给出一个主推荐的开发期隔离方案，并单列公开切换时真正需要Owner决定的旧入口／旧槽保留或显式清理承诺。设计必须覆盖：没有存档、合法新档、旧医院档、未知格式、已知格式但规则不支持、损坏档、读取失败、写入失败。

开发中“不改旧医院”的隔离，不等于永久维护两套完整游戏；不借写新版本默认删除旧槽，也不注册新生产格式／rulesVersion。可提出仅文档标识，但须明确没有发布、没有兼容生效。
