## 3. F01修复判断

### 原字段必须在覆盖前验证

`_validate_state`承载共享结构／数值校验；普通`validate`保持生还／已终局边界，内部`pending_action_death=True`只在死亡提案校验路径使用。`validate_death_proposal`先验证原base、独立current、原snapshot结构和原字段，再验证steps；通过后复制snapshot/steps，才交终局清退与关闭。

原revision的负数、bool、小数、unsafe、NaN/Infinity，以及错误任务execution、未知phase、畸形deathPoint，均不能被最终覆盖洗白。`same_data`比较类型与值，避免Python的bool／float与int相等产生越权。

### 合法死亡与未获权字段分开

有限producer既有职责只改变body.hp。因此它不得更改原revision、钱包、任务／声明、clock、关闭收据、既成历史、其他身体字段或实例／资源／容器。所有权检查在清退前进行，不要求最终dead状态与旧active逐字相同。

新增来源条件验证前态HP确在这份固定流血伤害可致死的范围；HP2不能通过伪造snapshot.hp=0冒充该来源死亡。这是固定模型的必要前后态约束，不是生产复算伤害，也不能照搬成所有真实动作只允许改HP。

### 步骤与对象保全

steps在索引前必须是非空字符串列表且等于本固定动作支持序列。空列表及非法元素／顺序语义拒绝，不崩溃、不靠捕获所有Exception取得通过。合法HP0一次消费；原提案对象不被清退逻辑改写。
