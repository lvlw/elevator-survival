## 4. F01：任务执行绑定和来源状态未联合校验（必须修）

定位：entry-004/validation/check.py，validate第48—62行、task消费第154—178行、return第224—229行；D01任务生产合同、D03来源分配条款。

validate目前主要检查单位总集合、别名及不重复；install按别名总数消费，没有核对任务件的execution。来源claimed状态也未与现存／已处分的来源单位建立完整关系。

固定反例：

| ID | 注入／实际观察 |
| --- | --- |
| foreign-execution-component-install | 先由模型component生产真实任务件，只改其execution为other-execution；仍安装、消费材料、令transfer为真 |
| foreign-execution-module-install | 同样仅改真实module的execution；仍产生安装后态 |
| missing-source-claim-install | 原单位仍在，却删除TASK-component的claimed事实；仍被接受并安装 |
| missing-sample-source-claim-return | 实际模型生产样本后删除其来源claimed事实；仍被接受为成功，积分120 |

这些是现有字段之间的矛盾，不要求离线反作弊、全历史认证或新任务SDK。对任务件限定本次具体执行，不把普通合法历史资产一概当非法外来物。

修复应在物品处分、完成事实和终局生成之前拒绝矛盾；保留真实来源、单位份额、实例归属和claimed的联合关系。单纯数目相等不够，但也不能删掉原有单位守恒，或将来源问题一律转成“不支持”。

必须保留：合法组件／模块安装、地面任务件拒绝、安装材料不足拒绝、原样样本成功、错执行／地面样本拒绝；普通剩余物、消费处分、拆合不能因此全部被禁。

## 5. F02：逐意图／原始字段校验不完整（必须修）

定位：check.py第114—117行、source第129行附近、task第155行、medical第189—211行及validate伤口子结构；原任务§6.2“非法数值覆盖前拒绝、语义拒绝不得由异常冒充”。

当前只有跨所有动作的总字段集合，未逐op收窄。用药不读取quantity，却允许该字段通过；expectedRevision只用Python相等比较。伤口treated子字段未严格校验，未知ID及缺少op直接字典索引。

固定观察：

- quantity=-1、True、0.5或9007199254740992的包扎请求均被接受：HP8→9，实际消耗一单位，revision递增。问题是非法请求被忽略字段后洗成合法结果，不是“负数量产生无限回血”。
- expectedRevision=False被当作revision0通过。
- medical夹带outcome='success'未拒绝。该字段没有真的发奖；问题在于动作字段隔离失效，不能夸大为客户端能设置成功。
- wounds中的treated=-1未拒绝，仍可产治疗后态。
- 缺op、未知source ID和未知task ID抛出KeyError，而非Reject。原run包装会把它们记modelError；这不等于整套脚本必定崩溃，更不属于正确语义拒绝。

应先验证意图对象、标签、该动作允许／必需字段、选择器存在性和数字类型，再查字典、产生效果。固定单单位用药可以不接受quantity，或严格限定为允许值；不得继续忽略非法数量。外部战斗条件字段须与普通玩家意图区分，不因其需要damage/outcome就让所有操作通用这些键。

只将预期业务错误转成稳定Reject。不得catch所有Exception并统一宣称通过；真正程序异常仍须单独暴露。
